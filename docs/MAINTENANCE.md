# 维护手册

本仓库的日常维护流程。设计目标：**只改一个 YAML，其余全自动**。

```
data/papers.yaml     ← 唯一数据源，只改这个
data/sections.yaml   ← 章节定义（中英标题 + 存量 + 检索关键词）
   ↓  scripts/build.py
README.md            英文主版本
README.zh-CN.md      中文副版本
docs/by-env/*.md     按环境分组（中英各 4 个）
```

**双语约定**：英文（`summary`）是主版本，中文（`summary_zh`）是等价副版本而非节译。
两者都是必填，CI 会拦缺失。

## 双周更新流程

### 为什么是双周而非周更

实测该方向 arXiv 增量约 **4.3 篇/周**，波动很大（实测有的周期只召回 1 篇）。周更会频繁空窗，
双周窗口约 9 篇召回、4–6 篇收录，节奏更稳。

**低谷周期不要为凑数放宽标准。** 2026.09.03–09.11 只召回 1 篇，这是领域真实节奏，
不是检索出问题（可比对 `fetch.py` 打印的「arXiv 报告命中 N 篇」确认）。
这种周期适合顺手补存量：挑当前最薄的小节做定向检索，见下文「存量建库」。

实测记录：

| 窗口 | 召回 | 收录 | 剔除 |
|---|---|---|---|
| 2026.09.26–10.02 | 8 | 4 | 4（纯能力向 2 / 多 agent 通用框架 1 / 可靠性视角 1） |
| 2026.09.19–09.25 | 2 | 2 | 0（低谷周期；顺带补存量 37 篇，详见「存量建库」第四轮） |
| 2026.09.12–09.18 | 6 | 4 | 2（纯能力向 1 / 用 agent 做安全 1；顺带补存量 9 篇） |
| 2026.09.03–09.11 | 1 | 1 | 0（低谷周期，顺带补存量 11 篇） |
| 2026.08.20–09.02 | 9 | 4 | 5（纯能力向 2 / 可靠性视角 3） |

### 步骤

**1. 确认上次实际覆盖到哪天**

不是上次「请求」到哪天。查库里最大的 arXiv ID：

```bash
grep 'id: "' data/papers.yaml | sort -t'"' -k2 -r | head -3
```

**当天投稿几乎必然未索引** —— 窗口终点写到今天没关系，但必须在 commit 里标明实际覆盖区间，
把缺的天留给下一轮起点。

**2. 检索候选**

```bash
python3 scripts/fetch.py 2026-09-03 2026-09-16
```

脚本会自动剔除库中已有 ID，输出 v1 日期、主分类、命中的形态词。

读候选摘要（批量，走 curl，含 comment 字段里的录用会议）：

```bash
python3 scripts/abstracts.py 2609.32915,2610.00450
```

若某小节想单独补历史存量：

```bash
python3 scripts/fetch.py 2024-01-01 2026-09-11 --section 1.2
```

**3. 人工判断范围（不能省的一步）**

对每篇候选问三个问题：

1. **主要研究对象**是 GUI/CUA/browser/mobile agent 吗？还是只把它当实验环境之一？
2. 主要贡献在**安全**吗？还是能力/可靠性/效率？
3. 把标题里的 "GUI agent" 换成 "LLM"，贡献是否依然成立？成立 → 不收。

实测常见的剔除类型：

| 类型 | 例子 | 判断 |
|---|---|---|
| 纯能力向技术报告 | UI-Venus-2 Technical Report | 剔 |
| 系统优化综述 | Efficient GUI Agents: A Systems Survey | 剔 |
| 可靠性/检测视角 | Monitoring Web Agents、Automated Trajectory Evaluation | 边界，倾向剔并在 commit 说明 |
| 反检测（攻方但非 agent 安全） | ActReal（对抗自动化检测） | 边界 |

**拿不准时收录 + 在 commit / PR 里列明理由**，不要自行删掉。但对「纯能力向」要果断剔除。

**4. 撰写条目**

读原文摘要（不要只看标题）：

```bash
curl -s "https://export.arxiv.org/api/query?id_list=2608.27808" | \
  python3 -c "import sys,re;raw=sys.stdin.read();print(' '.join(re.findall(r'<summary>(.*?)</summary>',raw,re.S)[0].split()))"
```

简介三段式：**动机 → 机制 → 关键数字**。数字要具体到指标名与数值。

**5. 校验并提交**

```bash
python3 scripts/build.py          # 生成产物 + 校验结构与锚点
python3 scripts/check_links.py    # 全量校验 arXiv 元数据
git diff --stat                   # 确认只动了预期文件
```

Commit message 模板：

```
Add N papers from YYYY.MM.DD to YYYY.MM.DD

新增（召回 X 篇，收录 N 篇）：
  §1.1 间接提示注入  方法名（一句话）
  §2.3 执行中拦截    方法名（一句话）

按范围剔除 M 篇：
  论文名 —— 理由

N 篇全部通过 arXiv 元数据校验。
```

### 批量建库的操作要点（实测）

**一批 6 篇为宜。** 读摘要 → 写双语简介 → 合并 → `build.py`，
一轮 6 篇既能保证简介质量，出错时回溯范围也小。

**合并一律用 `scripts/merge.py`，不要 `cat >>`。**

```bash
python3 scripts/merge.py /tmp/batch.yaml --dry-run   # 先看会新增几条
python3 scripts/merge.py /tmp/batch.yaml
python3 scripts/build.py
```

`merge.py` 在写入前按 arXiv ID / url 判重，已存在的条目直接跳过，**因此可以
安全地反复执行**。直接 `cat batch.yaml >> data/papers.yaml` 在命令重试或中断
重跑时会把同一批追加两次 —— 这个错误实测犯了两次。虽然 `build.py` 的重复校验
每次都拦住了，但事后截断修正容易多切或少切，不如从源头避免。

**每批合并后立刻跑 `build.py`。** 它会校验重复、必填字段、日期格式与锚点。
若积累多批再校验，定位问题段落会麻烦得多。

**全量 `check_links.py` 现在是批量查询，178 篇约 1 分钟（5 批 × 8s 间隔）。**
可以直接前台跑。

> 2026-09-18 之前它是逐条请求 + 3.2s 间隔，139 篇要 8 分钟，且在 CI 上会被
> arXiv 限流：实测定时任务里 126 条只有前 12 条通过、其余 114 条全部报
> 「无法访问或不存在」。改用 `id_list` 批量查询（40 条/批）后，请求数从 139 降到 4，
> 耗时降到 14 秒，限流风险基本消除。

**改完数据源后如果远端已有 Actions 提交，推送会被拒。** 标准处理：
```bash
git stash -q
git pull --rebase <URL> main
git stash pop
python3 scripts/build.py     # rebase 后必须重建
git push <URL> main
```

### ⚠️ 检索结果为 0 或偏少时，先怀疑工具再怀疑领域

`fetch.py` 每次运行都会打印一行 `arXiv 报告命中 N 篇，开始翻页…`。
**这行必须出现。** 若日志里只有「召回 0 篇」而没有这一行，说明首页请求根本没成功，
不是真的没有结果。

历史上这里连续踩过两个坑，都表现为「结果偏少但没有任何报错」：

| 时间 | 症状 | 真实原因 |
|---|---|---|
| 2026-09-04 | 全区间 253 篇只召回 100 篇，未收候选从 217 缩水成 76 | 硬编码 `start=0` 单次请求，arXiv 单次上限 100 条，超出部分被丢弃 |
| 2026-09-18 | 全区间召回 **0 篇**，日志显示「本窗口无新增」 | 首页网络请求失败，`_one_page()` 返回 `""`，`search()` 静默 `break` |
| 2026-09-25 | 任何窗口都失败，报 `HTTP Error 406` / `429`，重试十余次无效 | 查询串过长被 WAF 拒 + urllib 指纹被拒 + 频率限流，三因素叠加，见下节 |
| 2026-09-25 | 四轮建库后收录率反弹到 26%，冒出一批从未见过的奠基论文（WASP、SafeArena、RedTeamCUA…） | 同上 —— 查询串过长导致长期漏召回，此前「存量接近清完」的判断是错的 |

第二个坑尤其危险：当时刚好处在「存量接近清完」的阶段，0 篇很容易被误读为
**「存量已经全部收录完毕」**这一重大结论。重试一次即恢复正常（命中 281 篇）。

两处均已修复：
- 翻页循环直到某页不足 `page_size`，并在结束时自检「实际取到数 vs arXiv 报告总数」，
  不一致则打印截断警告
- 网络连续 4 次失败改为 `raise RuntimeError`，绝不返回空字符串伪装成无结果

**双周窗口（通常 <100 篇）不受分页问题影响**，所以这类 bug 只在长区间补存量时暴露。

### ⚠️ 406 / 429 的真实根因：查询串过长 + urllib 指纹

2026-09-25 这次排查绕了很久，结论值得完整记下来，因为**三个因素叠在一起，
每个单独看都像是对的**：

**因素一：查询串规模。** 原来的 `_one_page()` 把 9 个 `cat:` + 15 个形态词 +
13 个安全词拼成一条 981 字符的 URL。这条 URL 会被 arXiv 前置 WAF 稳定拒绝
（406/400），而把形态词砍到 3–4 个的短查询**全部 200**。修复：形态词按 4 个
一组分块检索（`FORM_CHUNK`），分类过滤挪到本地 `parse()` 里做 —— 这不影响
三层交集语义，只是把交集的一层从查询串移到了客户端。

**因素二：urllib 的请求指纹。** 同一条 URL、同一时刻，`curl` 得 200 而
Python `urllib` 得 406，连续重试 5 次全是 406，换 curl 立刻成功。所以
`fetch.py` 与 `check_links.py` 统一走 `http_get()`：**curl 优先、urllib 兜底**。

**因素三：请求频率。** 短时间连续十几次请求后会进入几分钟的拒绝期，期间
任何请求都返回 406 或 429。退避改为指数级（20/40/80/160s），`SLEEP` 默认
放宽到 15s（可用 `AGAS_SLEEP` 覆盖）。

排查顺序建议：**先用 curl 原样重放失败的那条 URL。**
- curl 200 → 是因素二，客户端问题
- curl 也失败，但砍短查询串后 200 → 是因素一
- 长短查询都失败，等几分钟后恢复 → 是因素三

**关键：406/429 期间不要下任何数据结论。** 它和「该窗口真的没有论文」在脚本
输出上无法区分，唯一可靠的区分方式是「arXiv 报告命中 N 篇」这行日志有没有打印。

### ⚠️ merge.py 曾静默清空 138 条数据

2026-09-25 的另一个坑，性质比上面严重得多。`merge.py` 无跳过项时会整段追加
批文件文本，而批文件顶层写着 `papers:` —— 于是 `papers.yaml` 里出现**两个顶层
`papers:` 键**，PyYAML 取最后一个，原有 139 条全部被解析丢弃，只剩新批次的 10 条。

**最危险的是它不报错。** `build.py --check` 会如实打印「✓ 校验通过：10 篇」，
所有校验（必填字段、重复、锚点）全部通过 —— 因为剩下的 10 条确实都合法。
如果没留意那个数字就直接 `git commit`，等于静默删库。

两道修复：
- `merge.py` 写入前剥掉批文件顶层的 `papers:` 键
- **合并后先在内存里校验再落盘**：顶层键必须恰好是 `["papers"]`，且条目数必须
  等于「原有 + 新增」，任一不符就报错退出、源文件保持不动

**教训：`build.py --check` 打印的篇数必须每次都看。** 它是唯一能发现这类
「数据被吞掉但格式合法」问题的信号。

### ⚠️ CI 上 Link Check 失败，先看是不是 406

**GitHub Actions 的出口 IP 经常被 arXiv 的 WAF 拒（HTTP 406），curl 与 urllib 都拒。**
这与数据无关 —— 本地同一份数据全部通过。历史上 Link Check 已因此误报三次
（run#17 限流、run#20 与 run#21 皆 406）。

「狼来了」是有代价的：CI 连续飘红之后，真出数据问题时反而没人认真看。所以
`check_links.py` 现在把网络故障与数据错误分开处理：

| 情况 | 行为 |
|---|---|
| 某批请求失败 | 记录后**继续跑其余批次**，不中断 |
| 全部批次失败 | 判定 arXiv 不可达，打印说明后 **exit 0**（不误报） |
| 部分批次成功 | 只校验取到元数据的条目，其余标「跳过」而非「不存在」 |

判断方法：看日志里的批次行。若全是 `批次 N 请求失败`，就是网络问题，
**本地重跑一次即可确认数据无误**。

这个放宽不会漏掉真问题：只要 arXiv 可达，标题不匹配与日期不一致照样让 CI 变红。

## 检索 query 的三个坑（实测）

**1. 三层交集不能省，但不必都塞进查询串。** 形态词 × 安全词 × 分类键，少任何一层
都会出问题：只用形态词混入能力向论文；只用安全词混入通用 LLM 安全；分类键不叠加前两层
则存量虚高数倍 —— 实测 `benchmark` 一项召回 726 篇，收紧后仅 143 篇（benchmark 在
能力向论文里是标配词）。

**注意交集在哪一层求。** 2026-09-25 起，形态词按 4 个一组分块发请求、分类过滤改在
本地 `parse()` 里做 —— 语义完全等价，但避免了查询串过长被 WAF 拒（见上节）。

**2. 不能强制 `AND security`。** 这类论文惯用 attack / injection / safety / hijack。
实测强制 security 使召回从 5.3 篇/周 压到 0.7 篇/周。

**3. 单个形态词都撑不起来。** computer-use agent 1.3/周、GUI agent 1.7/周、mobile 1.0/周、
web agent 0.3/周。必须用并集。

## 常见问题

**Q: 改了 papers.yaml 但 README 没变？**
跑 `python3 scripts/build.py`。或者推到 main 后由 Actions 自动重建。

**Q: CI 报「标题不匹配」？**
以 arXiv 返回的标题为准修改 yaml。这个检查专门拦 ID 写错和条目凭空编造 ——
实测同类仓库存在 arXiv ID 是 LLM 幻觉或 `26xx.XXXXX` 未回填占位符的情况。

**Q: CI 报「date 与 v1 不一致」？**
以 v1 为准。收录日期是**首次提交月**，不是 v2/v3 更新月。

**Q: CI 报一大批论文「无法访问或不存在」怎么办？**

**先假定是限流，不要删条目。** 判据很简单：几十上百篇论文不可能同时从 arXiv 消失。
典型特征是前若干条通过、之后连续全部失败 —— 这是速率限制的形状，不是数据错误的形状。

实测案例（2026-09-14 定时任务）：126 条里前 12 条通过、后 114 条全报「无法访问」，
而同一份数据在本地跑是 126/126 全过。原因是当时逐条请求，CI 共享出口 IP 更易触发限流。

处理顺序：
1. 本地重跑一次 `python3 scripts/check_links.py`（现在只需十几秒）
2. 若本地全过 → 判定为 CI 侧限流，重跑 workflow 即可
3. 只有当**个别**条目稳定失败时，才去核实该 arXiv ID 是否真的写错

脚本已加两道保护：批量请求连续 4 次失败直接抛错并提示「请勿据此删除条目」；
若所有批次都没返回任何条目，直接判定为请求异常而非数据错误并退出。

**Q: 某节长期没有条目怎么办？**
保留骨架，不要为凑数降低收录标准。ASI/威胁模型分类本身就是有价值的信号 ——
某节为空说明该攻击面研究稀缺，这是领域现状而非仓库缺陷。
